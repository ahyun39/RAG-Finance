구성요소를 역할 기준으로 분해

② 추출

Python (json)

  • src/extract.py — heading을 만날 때마다 새 레코드 시작
  • 청크 제목을 대제목 : 소제목으로 만들어 소제목도 임베딩 입력에 포함
  • 측정: MRR 0.642 → 0.683 (Recall@5는 0.817 → 0.812로 거의 같음)
  • 알려진 결함: HTML 번호·글머리 목록 항목이 유실되어 101청크 중 20개가 "다음의 …"에서 끊김
  • 출력 data/text_sections.json — 93레코드

③ 청킹

Structure-aware Chunking

  • 문장 단위로 나눈 뒤 목표 500자 · 최대 700자로 결합, 100자 미만 마지막 조각은 앞 조각에 병합
  • 크기 근거: docs/text_eda.ipynb의 길이 분포 EDA
  • 표는 길이와 관계없이 분할하지 않고 마크다운으로 직렬화한 1청크 (헤더-행 대응 보존)
  • 4,000자 초과 표에만 행 경계 분할 + 조각마다 헤더 반복 (현재 데이터에서는 미발동), _selfcheck()로 무손실 검사
  • 출력 data/chunks.json — 101청크 (표 8개), 길이 38 / 중앙 189 / 최대 1,853자

④ 임베딩 · 벡터 인덱스

sentence-transformersKURE-v1FAISS

  • nlpai-lab/KURE-v1 — 1024차원 · 8192토큰 · CLS 풀링 · Normalize 모듈 포함
  • 교체 이유: 이전 모델(ko-sroberta)의 실제 입력 상한이 128토큰이라 청크 46%가 잘림 → Recall@5 0.787 → 0.887
  • 인코딩 시 normalize_embeddings=True, 인덱스 구축 시 faiss.normalize_L2 → IndexFlatIP 내적 = 코사인
  • 전수 탐색(근사 탐색 미사용): 101청크 · 404KB 규모라 충분히 빠르고 근사 누락이 평가에 섞이지 않음
  • 계약: embeddings.npy 행 순서 = chunks_meta.json 순서, 적재 시 assert index.ntotal == len(meta)

⑤ 어휘 검색 · 융합

rank-bm25 BM25OkapiRegex TokenizerWeighted RRF

  • BM25Okapi 기본값 k1=1.5, b=0.75 — 앱 시작 시 chunks_meta.json으로 메모리에 구축
  • 정규식 토크나이저: 구두점·괄호 제거, 제39조의2제1항 → 제39조의2·제1항 원자 추출, 얕은 조사 분리(어간 2글자 이상), 원본 토큰 유지
  • 조문 번호 질의(제N조 · 제N항 · 제N호)만 어휘 가중치 0.3 → 1.0
  • RRF는 순위만 결합하고 결과의 score는 코사인으로 유지 — 게이트가 코사인 척도에서 동작
RRF(d) = 1/(k + rank_dense(d)) + w · 1/(k + rank_lex(d)), k = 10

⑥ 2단 답변 게이트

Abstention

  • gate() ① 상위 결과의 최고 코사인 ≥ 0.52여야 답변 (질문 단위)
  • ② 답하기로 정한 뒤 코사인 ≥ 0.44인 청크만 LLM 근거로 전달 (청크 단위)
  • 통과 청크가 없으면 LLM을 호출하지 않고 검색 결과만 표시
  • 이유: 질문 단위 최고 코사인 기준으로 정답 있는 질문 28개 중 17개가 무정답 범위와 겹쳐 단일 임계값으로 분리 불가(최적 분리 정확도 0.839)

⑦ 생성

Upstage Solar Pro3openai SDK

  • OpenAI 호환 API(base_url = api.upstage.ai/v1), 모델 solar-pro3, temperature 0.2, max_tokens 1024
  • build_context() — 통과 청크만 넣되 번호는 화면 카드 순서 기준 [참고 N]
  • 시스템 프롬프트 규칙 5개: 근거만 사용 · 없으면 확인할 수 없다고 안내 · 수치 계산·변환 금지 · [텍스트](URL) 인용 · 면책 문장
  • API 키가 없으면 검색 전용 모드로 동작

⑧ 후처리 · 서빙

Streamlit

  • 정규식 후처리: 링크 뒤에 붙은 조사를 띄움 (코드로 보장할 수 있는 규칙은 프롬프트에서 제외)
  • 고정 면책 문구 st.caption — LLM 출력과 무관하게 답변과 함께 표시
  • 출처 카드: [참고 N] · 유사도 점수, 표 청크(|로 시작)는 마크다운 표로 렌더링
  • 표시 개수 3 / 5 / 10 (기본 TOP_K = 5), 리소스는 st.cache_resource로 1회 로드

검색 지표만으로는 보이지 않는 영역
실패 유형실제 사례발생 레이어검색 지표에서 보이는가개선 방향

데이터 결함#7 — 금지 행위 목록(대가 수수 대여 포함)이 추출 단계에서 유실추출안 보임 (정답 청크는 1위)HTML 목록 요소 보존
어휘 함정코퍼스 어휘를 쓰지만 답이 없는 질문 9개 중 1개만 거부게이트거부율에 반영리랭커 또는 생성 단계 근거 검증
핵심: 검색 지표가 높아도 답변의 완전성과 데이터 무결성은 보장되지 않습니다. 그래서 정량 트랙과 별도로 실제 답변을 근거 원문과 대조하는 정성 트랙을 두었습니다. 생성된 9건 중 본문에 면책 문장을 넣은 답변은 4건이라, UI 고정 문구가 실제로 필요한 안전 장치임도 이 트랙에서 확인했습니다.
