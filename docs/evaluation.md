* 법령 용어 질문 10개
* 구어체 질문 10개 (생활법령정보 100문100답 기반, `eval/crawl_qna.py`로 수집)
* **조항 번호 질문 8개** (2026-08-28 추가) — 「예금자보호법」 제39조의2처럼 법령명+조문 번호로 묻는 형태. `st-08`은 법령명 없이 조문 번호만 주는 더 어려운 형태로, 의미 단서를 일부러 뺐습니다.
* 코퍼스에 답이 없어 거부가 정답인 질문 **28개** (2026-09-03에 10 → 28개로 확장)
  * 기존 10개 + **도메인 내 무관 9개**(실손보험·ISA·국민연금 등 금융이지만 코퍼스 주제 밖)
  * **어휘 함정 9개** — 코퍼스 어휘를 그대로 쓰면서 답은 없는 질문(「외화예금도 예금자보호 대상인가요?」, 「해외로 잘못 송금한 경우에도 착오송금 반환지원을 받나요?」). 모든 후보는 코퍼스 원문 키워드 검색으로 답의 부재를 사전 확인했습니다.

조항 번호 유형을 추가한 이유는 **지표가 보지 못하는 영역이 있다는 의심** 때문이었습니다. 임의로 던져 본 조항 번호 질의 3건에서 정답이 top-10에도 없는 것을 확인했는데, 기존 골든셋 20개 정답 문항 중 조항 번호를 포함한 질문이 0개라 이 실패가 어떤 지표에도 잡히지 않고 있었습니다. **고치기 전에 먼저 보이게 만드는 것**이 순서라고 판단했습니다.

`python eval/run_eval.py`로 측정합니다. 평가 단계에서는 LLM을 호출하지 않고 임베딩 검색 결과만 사용하므로 **LLM API 비용이 발생하지 않고, 동일한 모델과 입력에서는 결과가 결정론적입니다.**

청크 단위가 바뀔 때마다 골든셋 정답 라벨을 새 체계로 재판정했습니다(문항당 평균 정답 1.60 → 1.80 → 1.90개, 표 분할을 되돌린 현재는 다시 1.80개). **검색 결과를 확인하기 전에 라벨을 확정해, 결과에 맞춰 라벨을 조정할 여지를 없앴습니다.**

## 측정 지표

골든셋의 `answer_chunk_ids`가 참조 청크 라벨이므로, 아래 지표는 전부 LLM 판정 없이 계산됩니다. 초기에는 자체 명칭(전달률·거부 정확성)을 썼으나 2026-07-30에 표준 지표 체계로 정리했습니다.

| 지표 | 정의 | 비고 |
|---|---|---|
| **Hit Rate@5** | 정답 청크를 하나라도 상위 5건에 넣은 질문의 비율 | 검색기가 아예 실패한 질문을 골라냄 |
| **MRR@5** | 첫 정답이 나온 순위의 역수 평균 | "찾았는가"가 아니라 "얼마나 상위에 띄웠는가" |
| **Context Recall@5** | 참조 청크 중 상위 5건에 포함된 비율 | 청크 ID 기준 recall. RAGAS `context_recall`(LLM이 정답 문장 단위로 판정)과는 계산 방식이 다름. 예전의 Recall@5 |
| **Context Precision@5** | 순위 가중 정밀도 `Σ(Precision@i × 정답여부_i) / (top-5 안의 정답 수)` | RAGAS `context_precision` 공식을 LLM 판정 대신 청크 ID 라벨로 계산. 단순한 `정답 수 / 5`가 아님 |
| **nDCG@5** | 이진 gain 기준 순위 품질 | 정답 청크가 여러 개인 질문에서 MRR이 놓치는 뒤쪽 정답의 순위까지 반영 |
| **Context Recall@5 (post-filter)** | 참조 청크 중 답변 게이트를 통과해 LLM 컨텍스트에 실제로 들어간 비율 | **예전의 「전달률」.** 검색은 됐지만 게이트에 걸려 LLM이 못 보는 경우를 잡아냄 |
| **거부율 (Refusal Rate)** | 무정답 질문에서 게이트 통과 청크가 0개라 LLM 호출 자체를 건너뛴 비율 | **예전의 「거부 정확성」.** 이진 분류의 specificity(TNR)와 같은 정의. 거부해야 할 질문만을 분모로 하는 **비율**이므로 accuracy(양 클래스 합산)가 아닙니다 |

검색 지표(Hit Rate·MRR·Context Recall·Context Precision·nDCG)는 모두 정답 청크 ID를 relevance 1, 나머지를 0으로 두는 **이진 relevance** 기준입니다.

k=5는 앱의 검색 결과 수 **기본값**과 맞춘 값입니다(UI에서 3/5/10 선택 가능). 6위 정답은 기본 설정에서 없는 것과 같습니다.

거부율을 별도 지표로 둔 이유는 도메인 특성입니다. 법률 도메인에서는 잘못된 법률 정보를 생성하는 것이 답변을 거부하는 것보다 위험하므로, 적절한 상황에서 답변을 보류하는 능력을 검색 정확도와 분리해 측정합니다.

`eval/run_eval.py`는 실행 앞단에서 `_selftest()`로 Context Recall·Context Precision·nDCG·MRR 공식과 **@K 경계**(6위 정답이 top-5 지표에 새지 않는지)를 검증합니다. 지표 계산이 조용히 틀어지는 것을 막기 위한 회귀 방지 장치입니다.

## 개선 과정

### 1. 청킹 개선 전후 비교 (2026-07-27)

두 번의 청킹 개선을 각각 측정했습니다. ① heading(소제목) 단위 분리, ② 표를 행 경계에서 분할.

| 지표 | ① 이전 (58청크) | ① heading 분리 (101청크) | ② +표 분할 (106청크) |
|------|------|------|------|
| Recall@5 (전체) | 0.817 | 0.812 | 0.787 |
| MRR (전체) | 0.642 | **0.683** | 0.683 |
| 전달률 (전체) | 0.667 | **0.703** | 0.687 |
| Recall@5 (구어체) | 0.700 | **0.717** | 0.700 |
| MRR (구어체) | 0.483 | **0.517** | 0.517 |
| 전달률 (구어체) | 0.400 | **0.500** | 0.500 |
| 거부 정확성 | 0.200 | 0.200 | 0.200 |

> 이 표를 포함해 아래 과거 측정 기록은 당시 사용하던 자체 지표명(전달률·거부 정확성)을 그대로 둡니다. 현재 표준명과의 대응은 위 「측정 지표」 표를 참고하세요.

**① heading 분리**: Recall@5는 사실상 제자리(0.817 → 0.812)인데 MRR과 전달률이 함께 올랐습니다. 못 찾던 정답을 새로 찾아낸 것이 아니라, 이미 찾던 정답의 순위를 끌어올려 임계값을 넘기게 만든 개선입니다. 구어체 전달률 0.400 → 0.500이 가장 큰 변화로, 실제 앱에서 LLM이 근거 자료를 받는 비율이 올랐다는 뜻입니다. 의도한 대로 개선된 대표 사례는 law-08(접근매체의 양도·양수 금지)로, "접근매체 발급"과 "양도 등 금지"가 한 청크에 묶여 있어 MRR 0.50이었던 것이 분리 후 1.00이 되었습니다.

**② 표 분할**: 목적은 내용 소실 방지였고 그 목적은 달성했습니다(최대 표 청크 1853자 → 759자, 8개 표 전부 무손실 검증). 다만 **검색 지표는 오히려 소폭 하락했습니다.** 하락분은 전부 law-05와 col-02 두 문항에서 나왔는데, 이들의 정답 표가 2조각으로 나뉘면서 정답 청크 수가 2 → 3개로 늘었고 그중 뒷조각이 상위 5건에 들지 못했기 때문입니다. 표 자체는 여전히 검색되므로 검색 능력이 나빠진 것은 아니지만, 정답이 두 조각에 걸친 문항은 k=5에서 만점을 받기 어려워집니다. **지표를 올린 개선이 아니라 데이터 무결성을 확보한 개선**으로 읽는 것이 정확합니다.

> 이 표 분할은 2026-07-29에 **되돌렸습니다.** 임베딩 모델을 8192토큰으로 바꾸면서 표를 쪼갤 이유가 사라졌기 때문입니다(아래 「2차 시도」 참고). 현재 청크 체계는 위 표의 「① heading 분리 (101청크)」와 같습니다.

### 2. 임베딩 모델의 입력 상한 문제 (2026-07-27 발견 → 2026-07-29 해결)

표 분할 작업 중에 확인한 사실입니다. 코드 주석과 문서는 임베딩 모델의 상한을 512토큰으로 적어 두었으나, `jhgan/ko-sroberta-multitask`의 `max_seq_length` 실제 기본값은 **128토큰**(한국어 대략 200자)이었습니다. 당시 106개 청크 중 **49개(46%)가 벡터화 단계에서 뒷부분이 잘리고 있었습니다.** 목표 청크 크기 500자·최대 700자라는 설정 자체가 모델이 실제로 읽는 범위를 크게 벗어나 있었던 셈입니다.

같은 모델에서 `max_seq_length`만 512로 올려 잘림을 0건으로 만들어 봤을 때는 Recall@5와 MRR이 소수점까지 동일했고 전달률만 0.016 올랐습니다. **그래서 처음에는 "내용 소실은 실재하지만 검색 품질의 병목은 아니다"라고 결론지었는데, 이건 같은 모델 안에서만 맞는 이야기였습니다.** 모델 체급을 바꾸자 그림이 완전히 달라졌습니다.

### 3. 임계값 재조정과 임베딩 모델 교체 (2026-07-29)

거부 정확성 0.200이 두 번의 청킹 개선으로도 변화가 없어서, 검색기 자체가 아니라 **임계값과 모델**을 바꿔보고자 했습니다.

#### 1차 시도 — KF-DeBERTa 계열 (기각)

금융 도메인 말뭉치로 사전학습된 [KF-DeBERTa](https://huggingface.co/kakaobank/kf-deberta-base) 계열을 먼저 시도했습니다.

| 모델 | Recall@5 | MRR | 전달률 | 거부 |
|---|---|---|---|---|
| jhgan/ko-sroberta-multitask | **0.787** | 0.683 | **0.687** | 0.200 |
| upskyy/kf-deberta-multitask | 0.743 | **0.728** | 0.660 | 0.200 |
| kakaobank/kf-deberta-base | 0.475 | 0.392 | 0.475 | 0.000 |

**`kakaobank/kf-deberta-base`는 sentence-transformers 모델이 아니라 MLM 사전학습 인코더입니다.** 풀링 레이어가 없어 `SentenceTransformer`로 로드하면 학습되지 않은 평균 풀링이 임의로 붙습니다. 모델 카드의 KorSTS 85.99는 STS 파인튜닝을 거친 뒤의 점수이며, 그대로 임베딩에 쓰면 위처럼 무너집니다. 거부 정확성 0.000은 무정답 질문 10개 **전부**에서 근거가 임계값을 통과했다는 뜻입니다.

파인튜닝판(`upskyy/kf-deberta-multitask`)은 MRR만 앞설 뿐, **같은 임계값에서 비교하면** 운영점 0.60에서 전달률이 0.585 대 0.637로 뒤졌습니다. 거부 정확성 개선으로 보였던 것은 전부 임계값 몫이었고 모델 자체는 손해여서 되돌렸습니다.

#### 2차 시도 — 긴 컨텍스트 모델 (채택)

128토큰이라는 상한 자체를 없애는 방향으로 옮겼습니다. 청크 체계를 고정해 골든셋 라벨 재판정 없이 순수 모델 효과만 측정했습니다.

| 모델 | 차원 | seq_len | 잘리는 청크 | Recall@5 | MRR | 인덱싱 | 쿼리 |
|---|---|---|---|---|---|---|---|
| jhgan/ko-sroberta-multitask | 768 | 128 | **49/106** | 0.787 | 0.683 | 8s | 18ms |
| **nlpai-lab/KURE-v1 (채택)** | 1024 | 8192 | **0** | **0.887** | 0.808 | 313s | 58ms |

### 4. 하이브리드 검색 — "균일하게 섞으면 나빠진다" (2026-08-28)

조항 번호 질의가 지표 사각지대라는 것을 확인하고(위 「골든셋」), 골든셋에 `statute_ref` 8문항을 추가한 뒤 개선에 착수했습니다.

#### 먼저 측정한 베이스라인 — 예상이 절반만 맞았습니다

임의로 던져 본 조항 번호 질의 3건이 전부 실패했기에 이 유형 전반이 무너져 있으리라 예상했는데, **8문항으로 재 보니 Context Recall@5가 0.875였습니다.** 실패한 것은 st-01 하나뿐이었고, st-08은 정답을 1위로 찾고도 임계값(0.520 < 0.55)에서 걸린 별개 문제였습니다. 나머지 6문항은 질의에 담긴 의미 단서만으로 밀집 검색이 정답을 찾아냈습니다.

**"조항 번호 질의는 완전히 실패한다"는 것은 표본 3개에서 나온 과잉 일반화였습니다.** 골든셋을 먼저 만들지 않았다면 없는 문제를 고치는 데 시간을 썼을 것입니다.

#### 관례대로 붙였더니 전 지표가 나빠졌습니다

RRF의 관례값(k=60, 밀집:어휘 동등 가중)으로 결합한 결과입니다.

| 지표 | 밀집 검색 | RRF k=60, 동등 가중 |
|---|---|---|
| Context Recall@5 (전체) | 0.889 | **0.812** |
| MRR@5 | 0.827 | **0.768** |
| Context Recall@5 (구어체) | 0.850 | **0.683** |
| Context Recall@5 (조항 번호) | 0.875 | 0.875 |

**고치려던 조항 번호는 그대로인데 나머지가 무너졌습니다.** 원인은 두 가지였습니다.

1. **k=60이 101청크 코퍼스에는 너무 평평합니다.** RRF 점수는 `1/(k+순위)`라 k가 크면 1위와 20위의 차이가 거의 없어집니다. st-01에서 BM25는 정답(청크 42)을 **1위**로 찾았고 밀집 검색은 16위였는데, k=60에서는 이 격차가 뭉개져 정답이 상위 5건 밖으로 밀렸습니다. k=60은 원 논문(Cormack et al., 2009)이 파일럿 실험으로 고정한 값으로, 이 코퍼스에 맞춘 값이 아닙니다. k=10도 이 골든셋에서 고른 값이며 일반적인 최적값이라는 뜻은 아닙니다.
2. **신호가 없는 질의까지 BM25를 동등 가중하면 순위가 흐려집니다.** 구어체 질의에서 BM25 1위는 무관한 청크인 경우가 많았습니다(예: "계약을 잘못해서 취소하고 싶은데" → BM25 1위가 「금리인하 요구 요건」).

#### 조건부 가중으로 전환

밀집 검색이 이미 강한 이 코퍼스에서 어휘 검색은 **필요한 곳에서만** 강하게 쓰는 것이 맞다고 판단했습니다. 질의에 조문 번호(`제N조`, `제N항`, `제N호`)가 있으면 어휘 가중치를 올리고, 없으면 보조로만 섞습니다.

| 설정 | Recall@5 | statute_ref | post-filter | 거부 정확성 |
|---|---|---|---|---|
| 밀집 검색 (베이스라인) | 0.889 | 0.875 | 0.746 | 0.700 |
| RRF k=60, 동등 가중 | 0.812 | 0.875 | 0.657 | 0.700 |
| RRF k=10, 균일 w=0.3 | 0.925 | 0.875 | 0.746 | 0.700 |
| **RRF k=10, w=0.3 / 조문 w=1.0 (채택)** | **0.961** | **1.000** | 0.746 | 0.700 |

채택값은 k=5/10, 조문 가중치 1.0/2.0/3.0에서 모두 같은 결과가 나오는 **넓은 플래토 안쪽**이라 단일 지점 과적합은 아닙니다.

**표준 RRF와의 차이 (2026-10-01 확인)**: 밀집 검색과 BM25가 모두 101청크 전체를 순위화하므로 `search_hybrid`의 `missing` 처리(한쪽 순위에 없으면 최하위)는 실제로 실행되지 않습니다. 다만 BM25 점수가 0인 청크(예: law-01 질의에서 101개 중 46개)도 순위를 받아 어휘 항이 붙습니다. 원 정의처럼 목록에 없는 문서의 해당 항을 0으로 두는 표준형으로 바꿔 측정하면 Context Recall@5 0.961·MRR@5 0.848·Hit Rate@5 1.000은 같고, Context Precision@5 0.823 → 0.821, nDCG@5 0.847 → 0.846이며 56문항 중 39문항의 상위 5건이 완전히 같습니다. 서빙 코드는 바꾸지 않았습니다.

**통계적 검정**: 밀집 대비 문항별 Context Recall 차이의 페어드 부트스트랩 95% 신뢰구간은 **[+0.000, +0.179]**, 평균 +0.071입니다(문항 단위 재표본, 10,000회, percentile 방식, 2026-10-01 시드 0·42에서 동일하게 재현). 28문항 중 차이가 있는 문항이 2개(각 +1.0)뿐이라 하한이 정확히 0이 됩니다. **하한이 0에 닿으므로 "유의하게 좋아졌다"고 말할 수는 없습니다.** 채택 근거는 통계적 유의성이 아니라 ① 악화된 문항이 **0개**, ② 개선된 2문항(st-01, col-09)의 원인이 기계적으로 설명된다는 점입니다.

#### 임계값 게이트를 건드리지 않은 이유

하이브리드는 **순위만 바꾸고 `score` 필드에는 코사인 유사도를 그대로 남깁니다.** 가중합으로 점수를 섞었다면 결합 점수가 코사인과 다른 척도가 되어 `SIMILARITY_THRESHOLD`를 다시 잡아야 했을 텐데, 그 임계값은 이 앱의 거부(abstention) 안전장치입니다. 순위와 게이트를 분리한 덕분에 post-filter와 거부율이 **정확히 보존**되었습니다(둘 다 변화 없음).

이것이 post-filter Recall이 0.746에서 움직이지 않은 이유이기도 합니다. 검색은 좋아졌지만 새로 찾은 청크들이 임계값 아래에 있어 LLM까지 가지 못합니다.

#### 남은 문제: 병목이 검색에서 임계값으로 이동

Hit Rate@5가 1.000이 되어 **정답을 아예 못 찾는 질문은 사라졌습니다.** 남은 손실은 전부 임계값 게이트에서 발생합니다. 하이브리드 적용 후 임계값을 다시 쓸어 봤습니다.

| 임계값 | post-filter Recall | 거부 정확성 | 조화평균 |
|---|---|---|---|
| 0.50 | 0.913 | 0.400 | 0.556 |
| **0.52** | **0.782** | **0.700** | **0.739** |
| 0.55 (현재) | 0.746 | 0.700 | 0.722 |
| 0.60 | 0.711 | 0.900 | 0.794 |
| 0.62 | 0.711 | 1.000 | 0.831 |

**0.52가 현재 0.55를 지배합니다** — 거부 정확성은 0.700으로 같은데 post-filter Recall은 0.746 → 0.782로 높습니다. 그럼에도 **바꾸지 않았습니다.** 무정답 문항이 10개뿐이라 "거부 정확성이 같다"는 관측이 문항 하나로 뒤집힐 수 있고, 0.62의 거부 1.000을 과적합으로 보고 피하는 것과 같은 기준을 적용하면 0.52의 우위도 같은 표본에 기대고 있기 때문입니다. **골든셋의 무정답 문항을 늘린 뒤 확정할 사항으로 남깁니다.**

### 5. 설정값 단일화 — 주석은 실행되지 않는다 (2026-08-28)

### 6. 단일 임계값의 한계와 2단 게이트 (2026-09-03)

실사용에서 **관련 문서가 검색되는데도 답변이 나오지 않는** 사례가 보고되었습니다. 원인을 재기 위해 먼저 P0(무정답 문항 확장)을 처리했습니다.

#### 무정답 문항 10 → 28개

임계값을 10문항으로 고르고 있다는 것은 이전 판에서 이미 과적합 위험으로 지적한 사항입니다. 도메인 내 무관 9개와 어휘 함정 9개를 추가했고, 모든 후보는 **코퍼스 원문 키워드 검색으로 답의 부재를 사전 확인**했습니다.

확장하자마자 이전 결론 하나가 뒤집혔습니다. 「0.52가 0.55를 지배한다(거부 동일, 전달률만 높음)」는 관측은 **무정답 10문항에서만 성립**했고, 28문항에서는 0.52의 거부가 0.536, 0.55가 0.571로 갈렸습니다. 지배 관계가 아니라 교환 관계였습니다.

#### 근본 원인 — 두 분포가 겹친다

게이트는 질문마다 검색 결과의 최고 코사인 하나로 판단하므로, 같은 단위로 비교합니다.

| 질문 단위 최고 코사인 | n | 최소 | 중앙 | 최대 |
|---|---|---|---|---|
| 정답 있는 질문 | 28 | 0.517 | 0.696 | 0.860 |
| 무정답 질문 | 28 | 0.400 | 0.511 | 0.722 |

**정답 있는 질문 28개 중 17개가 무정답 질문의 점수 범위 안에 들어옵니다.** 최적 단일 임계값(0.653)에서도 분리 정확도는 0.839입니다(아래 표). 낮추면 무관한 근거가 새고, 높이면 관련 문서가 있는데도 답변이 안 나옵니다.

#### 「유사도를 높인다」는 방향은 측정으로 기각

점수 자체를 보정해 분리를 키울 수 있는지 확인했습니다. 질문 단위로 「답이 있음/없음」을 가르는 최적 정확도로 비교했습니다.

| 판별 신호 | 최적 분리 정확도 |
|---|---|
| **top1 코사인 (현재)** | **0.839** |
| top1 − 코퍼스 평균 | 0.804 |
| top1 − top5 최저 (점수 폭) | 0.750 |
| top1 z-score (분포 대비) | 0.696 |

**raw 코사인이 이미 최선이었습니다.** 질의별 점수 오프셋을 보정하는 정규화 계열은 전부 더 나빴습니다. 즉 "유사도를 높이는 후처리"는 이 모델·코퍼스에서 존재하지 않습니다.

#### 임계값을 조정하는 대신 판단을 쪼갬

단일 임계값이 두 개의 서로 다른 질문에 동시에 답하려 한다는 것이 문제였습니다.

* **「이 질문에 답할 수 있는가」** — 무관한 근거로 답하는 비용을 크게 두었으므로 높은 기준
* **「무엇을 근거로 넣을 것인가」** — 답하기로 정한 뒤에는 정답 근거를 놓치지 않도록 더 낮은 기준

두 번째 기준이 더 낮아야 한다는 것은 일반 법칙이 아니라, 오답 근거 유입을 더 무겁게 보는 이 시스템의 비용 판단에서 나온 선택입니다.

그래서 최고점으로 답변 여부를 먼저 정하고(`ANSWER_THRESHOLD = 0.52`), 답하기로 한 뒤에는 낮은 하한으로 근거를 모읍니다(`CONTEXT_FLOOR = 0.44`).

| 설정 | 답변 커버리지 | 전달률 | 거부(전체 28) | 거부(무관 19) |
|---|---|---|---|---|
| 단일 0.55 (이전) | 0.821 | 0.746 | 0.571 | 0.789 |
| 단일 0.50 | 1.000 | 0.913 | 0.393 | 0.579 |
| **2단 0.52 / 0.44 (채택)** | **0.929** | **0.889** | 0.536 | 0.737 |
| 2단 0.58 / 0.50 | 0.786 | 0.729 | 0.714 | 0.842 |

「거부(무관 19)」는 어휘 함정 9개를 뺀, **게이트가 명백히 막아야 할 질문만**으로 잰 값입니다. 이 기준에서 2단 0.52/0.44의 조화평균이 0.806으로 모든 후보 중 가장 높습니다.

**단일 0.50을 채택하지 않은 이유**: 커버리지는 1.000이 되지만 거부가 0.393으로 무너집니다. 0.55 → 0.50에서 새로 새는 일반 무정답 질문은 na-02(전세자금대출 → 「금리인하 요구 요건」), na-04(개인회생 → 「민원제기」), na-07(할부 항변권 → 「6대 판매원칙」), na-24(신용회복위원회 → 「분쟁조정 절차」)로, **명백히 잘못된 근거가 LLM에 전달됩니다**(어휘 함정 na-16까지 포함하면 5건). 2단 게이트는 같은 커버리지 개선의 대부분(0.821 → 0.929)을 얻으면서 이 중 3건을 계속 막습니다.

#### 남은 한계

* **어휘 함정은 거의 못 막습니다** — 9문항 중 1건만 거부. na-19(해외 착오송금)의 top1이 0.722로 대부분의 실제 정답보다 높습니다. 근거 청크가 주제상으로는 맞기 때문이며, 이 구분은 코사인으로 불가능합니다. 교차 인코더 리랭커나 생성 단계 Faithfulness 검증의 영역입니다.
* **col-07·st-08은 여전히 거부됩니다.** 게이트가 보는 값은 검색 결과의 **최고 코사인**이며, 그 기준으로 col-07은 **0.5170**, st-08은 **0.5196**입니다.
  * 하이브리드는 순위만 바꾸고 `score`는 코사인으로 남기므로 **1순위 청크가 최고 코사인 청크가 아닐 수 있습니다.** st-08이 그 경우로, 1순위는 0.4542지만 2순위인 정답 청크가 0.5196입니다. 56문항 중 **10문항**에서 둘이 갈리므로, 문턱을 논할 때 1순위 점수를 쓰면 틀린 결론이 나옵니다.
  * 문턱 부근을 최고 코사인으로 정렬하면 **st-08 0.5196 > col-07 0.5170 > na-07 0.5165 > na-02 0.5061 > na-04 0.5023**입니다.
  * **st-08은 코사인으로 갈라집니다.** 문턱 0.518이면 커버리지가 0.929 → **0.964**로 오르고 새는 무정답 문항은 **하나도 없습니다**(거부율 0.536 유지). 현재 0.52는 이 문항을 **0.0004 차이**로 버리고 있습니다.
  * **col-07은 갈라지지 않습니다.** 바로 아래 na-07이 **0.0005 차이**로 붙어 있어, col-07을 살리면 na-07이 함께 통과합니다(문턱 0.515: 커버리지 1.000, 거부율 0.500). 여기가 코사인 단일 신호의 실제 한계선입니다.
  * 다만 0.518은 **문항 하나에 기대는 관측**이라 아직 채택하지 않았습니다 — n=10에서 「0.52가 0.55를 지배한다」가 뒤집혔던 전례가 그대로 적용됩니다.
* **Context Recall@5 0.961의 손실은 두 문항에서만 나옵니다** — law-10(0.40, 정답 청크 69·71·72 누락)과 col-02(0.50, 청크 10 누락). col-02에서 빠진 청크는 14일 기한이 적힌 「청약의 철회 : 청약철회권 행사 기간 및 효력 (표)」로, **유사도 0.504로 컨텍스트 하한 0.44를 넘지만 하이브리드 순위 10위**라 기본 설정(상위 5건)에서 잘립니다. 게이트가 아니라 순위 문제이므로 리랭커(교차 인코더)의 영역입니다. (2026-10-01 재측정)
* **거부보다 불완전한 답변이 더 위험할 수 있습니다.** col-07·st-08처럼 거부된 질문은 사용자가 답을 받지 못했다는 사실을 압니다. 반면 col-02는 그럴듯한 답변이 나오지만 정작 알아야 할 기한이 빠져 있어, 사용자는 무엇이 누락됐는지 알 수 없습니다. 순위 개선을 임계값 손실보다 뒤로 미룰지는 이 차이를 함께 보고 판단해야 합니다.

### 7. 지표가 만점인데 답이 없는 청크 — 추출 단계 목록 유실 (2026-09-11 발견)

2026-09-11 재실행에서 col-06(「돈을 받고 체크카드를 빌려주었다 — 처벌받나요?」)의 답변이 질문의 핵심 조건인 **"돈을 받고"(대가 수수)**를 반영하지 못했습니다. 처음에는 생성 단계의 일반화로 보였으나, 근거 청크를 열어 보니 원인이 달랐습니다.

정답 청크(`chunk 35`)의 본문 **전체**입니다.

```text
누구든지 접근매체를 사용 및 관리함에 있어서 다른 법률에 특별한 규정이 없는 한
다음의 행위를 해서는 안 됩니다(「전자금융거래법」 제6조제3항 본문).
이를 위반하면 5년 이하의 징역 또는 3천만원 이하의 벌금에 처해집니다.
```

「다음의 행위」에 해당하는 **5개 항목이 통째로 없습니다** — ① 양도·양수 ② **대가를 수수·요구·약속하면서 대여** ③ 범죄 이용 목적 대여 ④ 질권 설정 ⑤ 알선·중개·광고. 원문 HTML의 번호 목록이 `src/extract.py` 단계에서 유실된 것으로, 코퍼스에 없는 내용을 LLM이 답할 방법은 없습니다.

**같은 패턴이 101청크 중 20개(20%)에서 발견됩니다.** 「다음의 …」로 끝나고 뒤에 목록이 없는 청크를 스캔한 결과입니다.

#### 왜 지표가 이걸 못 잡았는가

`chunk 35`를 정답으로 갖는 골든셋 문항은 law-08 · col-06 · st-04 세 개입니다. 그중 law-08의 측정값은 이렇습니다.

```text
YES  law-08  MRR=1.00  CtxRecall=1.00  CtxPrec=1.00  nDCG=1.00  post=1.00
```

**모든 검색 지표가 만점입니다.** 검색기는 정확히 제 일을 했고 — 정답으로 라벨된 청크를 1위로 찾아 게이트까지 통과시켰으니 — 지표상 흠이 없습니다. 그런데 그 청크에는 질문에 답할 내용이 없습니다.

Context Recall이 재는 것은 **「정답으로 라벨된 청크를 찾았는가」**이지 **「그 청크에 답이 들어 있는가」**가 아닙니다. 골든셋의 정답 라벨은 청크 ID이므로, 청크 내용이 비어 있어도 라벨만 맞으면 만점이 나옵니다. 「골든셋을 먼저 만들어 보이게 한다」는 이 문서의 원칙에도 **라벨 단위가 청크인 한 못 보는 층이 남는다**는 뜻입니다.

이 결함은 **파이프라인 1단계(추출)**의 문제이고, 검색·생성 어느 쪽을 고쳐도 해결되지 않습니다. 잡아내려면 답변-근거 대조(생성 단계 평가)나 추출 단계의 무결성 검사가 필요합니다.

**Faithfulness / Answer Relevancy**

시스템 프롬프트로 참고 자료 외의 내용을 답변하지 않도록 지시하고 있으나, LLM이 실제로 이를 지키는지 사후 검증하는 장치가 없습니다. 프롬프트 지침은 모델의 확률적 동작에 의존하기 때문에 100% 보장이 어렵습니다.

이 두 지표는 검색 지표와 달리 골든셋 라벨만으로는 계산되지 않고 LLM 판정이 필요합니다. 또한 심사 대상 답변을 평가 스크립트에서 재현하려면 `app.py`의 시스템 프롬프트를 공유해야 하는데, `app.py`가 최상위 Streamlit 스크립트라 import되지 않아 프롬프트와 `generate_answer`를 `src/`로 분리하는 작업이 선행되어야 합니다. 프롬프트를 평가 쪽에 복사하면 두 벌이 갈라져 측정값이 실제 서빙 동작과 달라지므로 택하지 않았습니다.

**Context Precision / Context Recall**

유사도 임계값 이상 청크만 LLM 컨텍스트에 전달되며, 관련 청크가 없으면 답변 생성 자체를 건너뜁니다(2026-07-02 적용). 금융 법령 특성상 유사 표현이 다른 맥락에서 반복되어 의미상 관련 없는 조항이 임계값을 넘는 문제가 실제로 확인되었고(거부율 0.200), 임베딩 모델 교체와 임계값 재조정으로 0.700까지 끌어올렸습니다(무정답 10문항 기준). 이후 무정답을 28문항으로 확장하면서 분모가 바뀌어 현재 값은 **0.536(전체 28) · 0.737(어휘 함정 제외 19)**입니다.

순위 기반 지표는 2026-07-30에 추가했습니다. 현재 값은 **Context Precision@5 0.823 · nDCG@5 0.847**로 둘 다 Context Recall@5 0.961보다 낮아, 남은 병목이 "정답을 못 찾는 것"이 아니라 "찾은 정답을 상위로 못 올리는 것"임을 가리킵니다.

**수치 정확성**

금액, 기간 등 수치 정보는 LLM이 변형하기 쉽고, 오류 시 직접적인 피해로 이어질 수 있는 항목입니다. 시스템 프롬프트에 수치를 직접 계산·변환하지 않고 참고 자료 그대로만 인용하도록 규칙을 두었으나(2026-07-02), 이는 확률적 완화책이며 생성된 답변의 수치를 원본 청크와 대조하는 결정론적 검증은 없습니다.

**Safety**

LLM 프롬프트 지침과 UI 고정 문구로 이중 방어를 구현했습니다. LLM이 면책 안내를 생략하더라도 사용자는 UI에서 반드시 해당 문구를 확인합니다.

다만 2026-09-11 재실행에서 **LLM이 면책 문장을 답변 본문에 넣은 것은 생성된 9건 중 4건**뿐이었습니다. UI 레이어가 받쳐 주므로 사용자에게 면책이 누락되지는 않지만, **프롬프트 레이어의 준수율은 절반에 못 미칩니다.** 이중 레이어가 실제로 필요했다는 근거이자, 프롬프트만으로는 보장되지 않는다는 실측이기도 합니다.

```python
# UI에 항상 표시 (LLM 동작과 무관)
st.caption("⚠️ 이 답변은 참고용 정보이며 법률 자문을 대체할 수 없습니다.")
```
