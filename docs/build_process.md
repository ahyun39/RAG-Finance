# RAG 검색 시스템 구축 과정

이 문서는 크롤링부터 서빙까지 이 시스템을 어떻게 만들었는지, 그리고 **각 구성요소가 오픈소스인지 상용 API인지, 온프레미스로 돌릴 수 있는지**를 정리합니다. 측정 지표와 개선 실험의 상세 근거는 [evaluation.md](evaluation.md), 커밋 단위 변경 이력은 [changelog.md](changelog.md)를 참고하세요. 이 문서는 "왜 이런 아키텍처를 선택했는가"에 집중합니다.

---

## 한눈에 보기

```
[오프라인 배치 — 수동 실행, 앱 실행과 무관]
easylaw.go.kr(공공 웹사이트)
        │  requests + BeautifulSoup4 (크롤링, 1회성)
        ▼
data/law_data.json
        │  extract.py (순수 Python — heading 단위로 레코드 분리)
        ▼
data/text_sections.json
        │  chunking.py (순수 Python — 길이 기준 분할, 표는 별도 청크)
        ▼
data/chunks.json
        │  embedding.py (sentence-transformers + KURE-v1, 로컬 GPU/CPU 연산)
        ▼
index/embeddings.npy, data/chunks_meta.json
        │  vector_search.py (FAISS — 인메모리 인덱스, 서버 없음)
        ▼
index/faiss_index.bin

[온라인 서빙 — streamlit run app.py 실행 중에만 동작]
사용자 질의
        │  KURE-v1로 쿼리 임베딩 (로컬)  +  BM25 어휘 검색 (로컬, 인메모리)
        ▼
가중 RRF로 두 순위 결합 (로컬) → 2단 게이트 (0.52 / 0.44)
        │
        ├─ 게이트 통과 청크 없음 → LLM 호출 생략, 검색 결과만 표시
        │
        └─ 통과 청크 있음 → Upstage Solar Pro3 API 호출 (외부 클라우드, 유일한 인터넷 의존)
                ▼
           답변 생성 + 출처 표시
```

핵심만 먼저 말하면: **위쪽 절반(크롤링~인덱싱)과 검색 단계는 전부 오픈소스 라이브러리로 로컬에서 실행되고, 인터넷이 필요한 지점은 데이터를 처음 모을 때와 답변을 생성할 때 딱 두 곳뿐입니다.** 자세한 근거는 아래 "온프레미스 vs 오픈소스" 절에서 구성요소별로 표로 정리합니다.

## 단계별 구축 과정

### 1. 크롤링 — `src/crawling.py`

`requests` + `BeautifulSoup4`로 국가법령정보센터의 생활법령정보(easylaw.go.kr)에서 금융 관련 콘텐츠를 수집합니다. 이 사이트는 페이지 하나가 아니라 `csmSeq`(주제 그룹) · `ccfNo` · `cciNo` · `cnpClsNo` 조합으로 콘텐츠가 나뉘어 있어, HTML의 CSS 클래스(`plv1a`=대제목, `plv2a`=소제목, `plv3a`=본문, `tplv2d`=주석, `tplvN`=표)를 파싱해 구조화된 JSON(`law_data.json`)으로 저장합니다.

이 단계는 **앱이 실행 중일 때는 전혀 호출되지 않는 1회성 배치 작업**입니다. 한 번 수집한 뒤 결과 파일이 저장소에 커밋되어 있어, 데모를 돌리는 사람이 다시 크롤링할 필요가 없습니다.

### 2. EDA — `docs/text_eda.ipynb`

`pandas`, `seaborn`, `matplotlib`, `kiwipiepy`(한국어 형태소 분석기)로 텍스트 길이 분포와 명사 빈도를 분석해 청킹 파라미터(목표/최대/최소 길이)의 근거를 만들었습니다. 마찬가지로 1회성 분석이며 결과물(파라미터 값)만 `chunking.py`에 반영됩니다.

### 3. 추출 — `src/extract.py`

`law_data.json`의 body 블록을 순회하면서 `heading`을 만날 때마다 새 레코드를 시작합니다. 처음에는 한 섹션의 모든 소제목·본문을 통째로 이어 붙여서 "이 문장이 어떤 소제목에 속하는지" 정보가 사라지는 문제가 있었는데, heading 단위로 레코드를 쪼개도록 바꿔 청크 제목에 소제목이 살아남게 했습니다(38 섹션 → 93 레코드). 외부 의존성 없는 순수 Python 로직입니다.

### 4. 청킹 — `src/chunking.py`

목표 500자 / 최대 700자로 문장 단위 분할합니다. `MIN_CHUNK_SIZE=100`은 섹션을 쪼갠 마지막 조각에만 적용되는 병합 기준이라 실제 최소 청크는 38자입니다(중앙값 189자). 표는 원칙적으로 **분할하지 않고 청크 1개 = 표 1개**로 유지합니다 — 표가 잘리면 헤더와 행의 대응이 끊겨 사실상 못 쓰게 되기 때문입니다. `MAX_TABLE_CHUNK_SIZE`(4000자)를 넘는 비정상적으로 큰 표에 한해서만 행 경계에서 분할하고 각 조각에 헤더를 반복시키는 안전장치를 뒀습니다. 이 로직도 외부 라이브러리 없이 표준 라이브러리(`re`, `json`)만으로 작성했습니다.

### 5. 임베딩 — `src/embedding.py`

`sentence-transformers` 라이브러리로 `nlpai-lab/KURE-v1` 모델을 불러와 `chunk_title + chunk_content`를 벡터화합니다. 이 모델은 Hugging Face Hub에 공개된 **오픈소스 사전학습 모델**로, 최초 1회(약 2.2GB) 내려받으면 이후에는 로컬 CPU/GPU에서 완전히 오프라인으로 추론합니다.

원래는 `jhgan/ko-sroberta-multitask`를 썼는데, 실제 최대 입력 길이가 문서상 512토큰이 아니라 **128토큰**이어서 청크 106개 중 49개(46%)가 벡터화 단계에서 잘리고 있었습니다. 8192토큰을 지원하는 KURE-v1로 교체해 잘림을 없앴고, 이 교체가 측정한 모든 지표를 동시에 끌어올린 유일한 변경이었습니다(자세한 비교는 evaluation.md).

### 6. 인덱싱과 하이브리드 검색 — `src/vector_search.py`

`faiss-cpu`의 `IndexFlatIP`(내적 기반)로 인덱스를 만듭니다. 임베딩을 `normalize_embeddings=True`로 이미 정규화했지만, 저장·재로드 과정에서 생길 수 있는 정밀도 손실에 대비해 인덱스 구축 시 `faiss.normalize_L2`를 한 번 더 적용합니다(이중 정규화). 정규화된 벡터의 내적은 코사인 유사도와 같습니다.

FAISS는 **별도 서버가 필요 없는 라이브러리**입니다. Milvus·Weaviate·Pinecone 같은 벡터 DB와 달리 인덱스 파일(`faiss_index.bin`)을 그대로 읽어 파이썬 프로세스 메모리에 올려 쓰는 방식이라, 배포·운영 관점에서 별도 인프라가 필요 없습니다.

여기에 **BM25 어휘 검색(`rank-bm25`)을 더해 가중 RRF로 결합**합니다. 밀집 벡터는 `제39조의2` 같은 저빈도 정확 토큰을 풀링 과정에서 잃는 반면 BM25는 그런 질의에 강해서, 둘을 합치면 서로의 약점을 덮습니다. 다만 **균일하게 섞으면 오히려 나빠지는 것을 측정으로 확인**해(Context Recall@5 0.889 → 0.812) 질의에 조문 번호가 있을 때만 어휘 가중치를 올리는 조건부 방식으로 바꿨습니다(자세한 근거: [evaluation.md](evaluation.md) 개선 과정 4).

BM25도 FAISS와 마찬가지로 **순수 파이썬 인메모리 인덱스**라 서버가 필요 없고, 앱 시작 시 101청크에서 즉시 구성됩니다. 즉 검색 스택 전체가 여전히 외부 의존성 0입니다.

설정값(`MODEL_NAME`, `TOP_K`, RRF 파라미터, 게이트 두 값)은 `src/config.py` 한 곳에만 있고 앱·파이프라인·평가가 모두 여기서 가져옵니다. 예전에는 파일마다 상수를 복사해 두고 주석으로 일치를 요구했는데, 실제로 어긋난 적이 있어 임포트로 바꿨습니다.

### 7. 서빙 — `app.py`

Streamlit으로 검색 UI를 만들고, 사용자 질의를 같은 KURE-v1 모델로 임베딩해 FAISS 순위와 BM25 순위를 RRF로 결합해 top-k를 찾습니다. 게이트는 2단입니다 — 최고 코사인이 `ANSWER_THRESHOLD`(0.52)에 못 미치면 **답변 자체를 생략**하고, 넘으면 `CONTEXT_FLOOR`(0.44) 이상 청크를 근거로 모읍니다. 하한 미만 청크도 UI에는 표시합니다. 단일 임계값으로는 정답 청크와 무정답 질문의 점수 분포가 겹쳐 가를 수 없다는 측정 결과에서 나온 구조입니다(자세한 근거: [evaluation.md](evaluation.md) 개선 과정 6). 통과한 청크가 있으면 Upstage Solar(`solar-pro3`, OpenAI 호환 API)를 호출해 답변을 생성하고, 링크 뒤 조사 분리 같은 결정론적으로 보장 가능한 부분은 프롬프트가 아니라 정규식 후처리로 처리합니다.

`UPSTAGE_API_KEY`가 없으면 `load_llm_client()`가 `None`을 반환하고, 이후 로직은 LLM 호출을 건너뛰고 검색 결과만 보여줍니다 — 이 상태가 이 시스템이 도달할 수 있는 **완전 온프레미스/오프라인 모드**입니다.

## 온프레미스 vs 오픈소스 — 구성요소별 정리

"오픈소스로 만들었다"와 "온프레미스로 돌아간다"는 다른 질문입니다. 오픈소스 라이브러리를 썼어도 상용 클라우드 API를 호출하면 그 순간 온프레미스가 아닙니다. 이 시스템은 아래처럼 **거의 전부 오픈소스 + 로컬 실행이고, 답변 생성 한 곳만 상용 클라우드 API**입니다.

| 구성요소 | 기술 | 소스 | 실행 위치 | 네트워크 필요 시점 | 온프레미스 가능? |
|---|---|---|---|---|---|
| 크롤링 | `requests`, `BeautifulSoup4` | 오픈소스 라이브러리 | 로컬 프로세스 | 최초 데이터 수집 시 1회 (easylaw.go.kr) | ✅ (수집 후 오프라인) |
| EDA | `pandas`, `seaborn`, `matplotlib`, `kiwipiepy` | 오픈소스 | 로컬 | 불필요 | ✅ |
| 추출·청킹 | 직접 작성한 순수 Python | 자체 코드 | 로컬 | 불필요 | ✅ |
| 임베딩 모델 | `nlpai-lab/KURE-v1` (`sentence-transformers`) | 오픈소스 사전학습 모델 (Hugging Face Hub 공개) | 로컬 CPU/GPU | 최초 1회 다운로드(~2.2GB) 이후 불필요 | ✅ (캐시 후 완전 오프라인) |
| 벡터 검색 | FAISS `IndexFlatIP` | 오픈소스 라이브러리 | 로컬, 서버 없이 인프로세스 | 불필요 | ✅ |
| 어휘 검색 | `rank-bm25` (BM25Okapi) | 오픈소스 라이브러리 | 로컬, 순수 파이썬 인메모리 | 불필요 | ✅ |
| 웹 UI | Streamlit | 오픈소스 프레임워크 | 로컬 프로세스(자체 서버) | 불필요(로컬/사내망 접속 시) | ✅ |
| **답변 생성 LLM** | **Upstage Solar Pro3** | **상용 클로즈드 모델** | **Upstage 클라우드** | **매 질의마다 필요** (API 키 + 인터넷) | **❌ 불가능** |

## 결론: 이 시스템은 온프레미스인가?

**검색(retrieval) 파이프라인은 100% 오픈소스 구성요소로 이루어져 있고, 임베딩 모델을 한 번 내려받고 나면 완전히 오프라인·온프레미스로 구동할 수 있습니다.** 자체 서버가 필요한 구성요소가 하나도 없다는 점(FAISS도 인프로세스 인덱스, Streamlit도 자체 내장 서버)도 온프레미스 배포를 쉽게 만드는 요인입니다.

**다만 "AI 답변 생성" 기능은 Upstage Solar Pro3라는 상용 클라우드 API에 의존하며, 이 모델은 오픈소스가 아니고 자체 호스팅도 불가능합니다.** `UPSTAGE_API_KEY`가 없으면 앱은 자동으로 검색 전용 모드로 내려가는데(`app.py`의 graceful degradation), 이 상태가 이 시스템이 낼 수 있는 유일한 100% 온프레미스 모드입니다. API 키를 넣고 답변 생성 기능을 쓰는 순간, 시스템은 더 이상 순수 온프레미스가 아니게 됩니다.

한 문장으로 요약하면: **오픈소스 기반 + 온프레미스 가능한 검색 엔진에, 답변 생성만 상용 클라우드 LLM을 얹은 하이브리드 구조**입니다. 완전 온프레미스로 전환하려면 Upstage 호출부를 자체 호스팅 오픈소스 LLM(예: vLLM으로 서빙하는 한국어 sLLM)으로 교체하면 되고, `generate_answer` 함수가 이미 OpenAI 호환 클라이언트 인터페이스로 분리되어 있어 교체 지점은 명확합니다 — 다만 현재 코드베이스에는 구현되어 있지 않습니다.

### 데이터 출처 관련 참고

크롤링 대상인 easylaw.go.kr(국가법령정보센터 생활법령정보)은 공공기관이 운영하는 무료 공개 사이트입니다. 유료 API가 아니라 일반 웹페이지를 HTML 파싱으로 읽어오는 방식이며, 이 프로젝트는 정보 제공·학습 목적의 비상업적 참고용으로만 사용합니다.
