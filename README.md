# 금융 법령 정보 검색 시스템 (RAG)

생활법령정보(easylaw.go.kr)의 금융 관련 법령 콘텐츠를 수집하고, 의미 기반 검색과 AI 답변 생성을 결합한 RAG(Retrieval-Augmented Generation) 시스템을 직접 구현했습니다.

"답변이 실제로 믿을 만한가?", "검색이 제대로 동작하는가?"를 **골든셋 56문항으로 정량 측정**하고, 측정값을 근거로 개선한 과정을 함께 기록했습니다.

---

## 최종 성과

골든셋 **56문항**(정답 있는 질문 28 + 답이 없는 질문 28) 기준. 임베딩 검색만 사용하므로 LLM API 비용 없이 **결정론적으로 재현**됩니다.

```bash
python eval/run_eval.py            # 서빙과 동일한 하이브리드 검색
python eval/run_eval.py --dense    # 밀집 검색 전용 베이스라인
```

### 검색 품질 — 밀집 vs 하이브리드

두 열 모두 **현재 게이트를 적용한 상태**이므로 위 두 명령으로 그대로 재현됩니다.

| 지표 | 밀집 검색 | **하이브리드(현재)** | |
|---|---|---|---|
| Hit Rate@5 | 0.929 | **1.000** | 정답 청크를 상위 5건에 넣은 질문 비율 |
| Context Recall@5 | 0.889 | **0.961** | 참조 청크 중 검색된 비율 (RAGAS non-LLM) |
| MRR@5 | 0.827 | **0.848** | 첫 정답 순위의 역수 평균 |
| nDCG@5 | 0.818 | **0.847** | 정답이 여러 개인 질문의 순위 품질 |
| Context Precision@5 | 0.810 | **0.823** | 순위 가중 정밀도 (RAGAS non-LLM) |

유형별 Context Recall@5 — 법령 용어 0.940 / 구어체 0.950 / **조항 번호 1.000**

### 답변 게이트 — 단일 임계값 vs 2단

두 열 모두 **하이브리드 검색**을 쓰고 게이트만 다릅니다. 왼쪽은 이전 방식이라 현재 코드로는 재현되지 않으며, 스윕 기록은 [docs/evaluation.md](docs/evaluation.md) 개선 과정 6에 있습니다.

| 지표 | 단일 임계값 0.55 | **2단 게이트(현재)** | |
|---|---|---|---|
| 답변 커버리지 | 0.821 | **0.929** | 정답이 있는 질문 중 실제로 답변이 생성된 비율 |
| Context Recall@5 (post-filter) | 0.746 | **0.889** | 게이트를 통과해 LLM에 실제 전달된 비율 |
| Context Recall@5 (구어체, post-filter) | 0.550 | **0.850** | 구어체 질문에서의 전달률 |
| Abstention Accuracy | 0.571 | 0.536 | 답이 없는 질문에서 답변을 거부한 비율 |

> 무정답 문항을 10 → 28개로 늘린 뒤의 값이라, 이전 판에 적혀 있던 Abstention 0.700과는 분모가 다릅니다. 거부가 0.571 → 0.536으로 내려간 것은 **어휘 함정 문항을 새로 넣었기 때문**이며, 게이트가 명백히 막아야 할 19문항만 보면 0.789 → 0.737입니다(「남은 과제」 참고).

> 청킹 개선·임베딩 모델 교체로 얻은 이전 개선분(Context Recall@5 0.817 → 0.895 등)은 **30문항** 골든셋에서 측정한 값이라 위 표와 분모가 다릅니다. 해당 이력은 [docs/evaluation.md](docs/evaluation.md)에 그대로 남겨 두었습니다.

**핵심 판단 4가지**

1. **임베딩 모델 교체가 유일하게 모든 지표를 동시에 올렸습니다.** 사용하던 모델의 실제 입력 상한이 문서에 적힌 512토큰이 아니라 **128토큰**이었고, 청크 106개 중 **49개(46%)가 벡터화 단계에서 잘리고** 있었습니다. 8192토큰 모델(`KURE-v1`)로 바꾸자 잘림 0건.
2. **금융 도메인 특화 모델은 측정해 보고 기각했습니다.** `kakaobank/kf-deberta-base`는 풀링 레이어가 없는 MLM 인코더라 그대로 쓰면 검색이 무너지고(Recall@5 0.475), 파인튜닝판도 같은 임계값에서는 기존 모델에 뒤졌습니다. "도메인 특화"라는 이름만으로 채택하지 않았습니다.
3. **하이브리드 검색은 "균일하게 섞으면 오히려 나빠진다"를 측정으로 확인하고 조건부로 바꿨습니다.** 밀집+BM25를 관례값(RRF k=60, 동등 가중)으로 결합했더니 Context Recall@5가 **0.889 → 0.812로 떨어졌습니다.** 밀집 검색이 이미 강해서, 신호가 없는 질의에까지 BM25를 같은 비중으로 섞으면 순위가 흐려지기 때문입니다. 반면 조문 번호 질의에서는 BM25가 정답을 1위로 찾는데 밀집 검색은 16위였습니다. 그래서 **질의에 조문 번호가 있을 때만 어휘 가중치를 올리는** 방식으로 바꿔 Recall@5 0.961, 악화 문항 0건을 얻었습니다.
4. **단일 임계값으로는 답할 수 있는 질문과 없는 질문을 가를 수 없습니다.** 무정답 문항을 28개로 늘려 측정해 보니 정답 청크 42개 중 **29개가 무정답 질문 top1 점수 범위 안**에 들어옵니다. 임계값을 낮추면 무관한 근거가 새고, 높이면 관련 문서가 있는데도 답변이 안 나옵니다. z-score·평균차감 같은 점수 정규화도 전부 시도했으나 **raw 코사인이 여전히 최선의 판별 신호**였습니다(분리 정확도 0.839 vs 0.696~0.804). 그래서 임계값을 조정하는 대신 **판단을 둘로 쪼갰습니다** — 「답할 수 있는가」는 최고점으로(0.52), 「무엇을 근거로 넣을까」는 낮은 하한으로(0.44). 답변 커버리지 0.821 → 0.929, 전달률 0.746 → 0.889.

## 데이터 파이프라인

각 단계는 독립 실행 스크립트이고 **데이터는 파일로만 주고받습니다.** 순서대로 실행하면 `app.py`가 쓰는 산출물이 만들어집니다.

다만 설정값은 예외입니다 — `src/embedding.py`·`src/vector_search.py`·`app.py`·`eval/run_eval.py`는 `src/config.py`를 임포트하고, `app.py`와 `eval/run_eval.py`는 검색 함수도 `src/vector_search.py`에서 가져옵니다. 상수를 파일마다 복사해 두었다가 실제로 값이 갈라진 적이 있어(2026-08-28) 임포트로 바꾼 결과입니다. `crawling.py`·`extract.py`·`chunking.py`는 내부 임포트가 전혀 없습니다.

| 단계 | 스크립트 | 산출물 |
|---|---|---|
| 1. 크롤링 | `src/crawling.py` | `data/law_data.json` |
| 2. EDA | `docs/text_eda.ipynb` | (청킹 파라미터 결정) |
| 3. 추출 | `src/extract.py` | `data/text_sections.json` |
| 4. 청킹 | `src/chunking.py` | `data/chunks.json` |
| 5. 임베딩 | `src/embedding.py` | `index/embeddings.npy`, `data/chunks_meta.json` |
| 6. 인덱스 구축 | `src/vector_search.py` | `index/faiss_index.bin` |
| 7. 서비스 | `app.py` | Streamlit 앱 |

**설계상 중요한 결정**

* **heading을 만날 때마다 새 레코드를 시작합니다.** 기존에는 섹션의 소제목을 별도 리스트로 모으고 본문을 통째로 이어 붙여, 어떤 소제목에 속한 내용인지 알 수 없었습니다. 청크 제목이 `대제목 : 소제목` 형식이 되고 `embedding.py`가 제목도 함께 임베딩하므로, 소제목이 검색 신호로 쓰입니다 (38 섹션 → 93 레코드 → 101 청크).
* **표는 1개 = 청크 1개로 유지합니다.** 표가 청크 경계로 잘리면 헤더와 행의 대응이 끊겨 사실상 못 쓰게 됩니다. `MAX_TABLE_CHUNK_SIZE`(4000자)를 넘는 비정상적으로 큰 표만 행 경계에서 분할하고 조각마다 헤더를 반복하는 안전장치를 두었으며, 현재 데이터(최대 1853자)에서는 동작하지 않습니다.
* **청크 크기 500자 / 최대 700자** — `docs/text_eda.ipynb`의 길이 분포 분석에서 도출했습니다. `MIN_CHUNK_SIZE=100`은 **한 섹션을 쪼갠 결과의 마지막 조각**에만 적용되는 병합 기준입니다(섹션 자체가 짧으면 heading 분리 효과를 지키려고 병합하지 않습니다). 그래서 실제 최소 청크는 38자이고, 실측 분포는 중앙값 189자 / 최대 1853자입니다.

## 남은 과제

* **어휘 함정에서의 거부 (최우선)** — 코퍼스 어휘를 그대로 쓰면서 답은 없는 질문(예: 「외화예금도 예금자보호 대상인가요?」, 「해외 착오송금도 반환지원 되나요?」)은 게이트가 거의 막지 못합니다(9문항 중 1건). 근거 청크가 주제상으로는 맞기 때문이며, 코사인 점수로는 원리적으로 구분되지 않습니다. 리랭커(교차 인코더)나 생성 단계의 Faithfulness 검증이 필요한 지점입니다.
* **여전히 답변되지 않는 질문** — col-07(최고 코사인 0.5170)·st-08(**0.5196**)은 답변 문턱 0.52에 못 미쳐 거부됩니다. st-08은 **0.0004 차이**로 걸립니다. 그렇다고 문턱을 낮출 수는 없습니다 — 바로 아래에 na-02(0.5061)·na-04(0.5023) 같은 무관 질문이 붙어 있어, 이 둘을 살리려면 그것들도 함께 통과시켜야 합니다. 점수만으로는 더 이상 갈라낼 수 없는 지점입니다.
* **순위 품질** — nDCG@5 0.847 < Context Recall@5 0.961. 정답을 찾고도 상위로 못 올리는 질문이 남아 있습니다. 다만 위 임계값 손실이 더 크므로 리랭커는 그다음입니다.
* **Faithfulness / Answer Relevancy 미측정** — LLM 판정이 필요하고, `app.py`가 최상위 Streamlit 스크립트라 시스템 프롬프트를 평가 스크립트에서 재사용할 수 없습니다. 프롬프트와 `generate_answer`를 `src/`로 분리하는 작업이 선행되어야 합니다.
* **수치 정확성** — 프롬프트에 계산 금지 규칙을 두었으나, 생성된 답변의 수치를 원본 청크와 대조하는 결정론적 검증은 없습니다.
* **골든셋 크기** — 무정답 문항을 28개로 늘려 게이트를 다시 골랐습니다(이전에는 10개). 다만 정답 있는 질문 28개는 그대로라 문항 하나가 지표를 3~5%p 움직입니다. 하이브리드 개선분(Context Recall@5 +0.072)도 페어드 부트스트랩 95% 신뢰구간이 [+0.000, +0.179]로 하한이 0에 닿습니다 — 악화된 문항이 0개라는 점이 채택 근거이지, 통계적으로 유의하다는 뜻은 아닙니다.
